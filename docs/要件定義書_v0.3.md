<scope>
## 1. システム概要

### 1.1 目的
自宅の食材在庫を一元管理し、家族構成・在庫状況・ユーザー要望を考慮した1週間献立を自動提案するエージェントシステム。

### 1.2 想定利用シナリオ
- 朝、冷蔵庫を開けながらスマホで在庫確認
- 買い物前に在庫照会と献立確認
- 週末に翌週の献立計画
- **使用優先度の高い食材（期限切迫品など）から、その場でレシピを1〜3案提案（v0.3新規）**
- 食材使用時の数量更新（消費記録）
- 賞味期限の確認（画面上の警告表示）

### 1.3 利用者
- 主操作者: 夫婦2名（共有アカウント）
- **MVPでの食事対象: 大人2名**
- 離乳食対応はPhase 2以降

### 1.4 利用環境
- **MVP**: 自宅Wi-Fi接続時のみ（LAN内限定）
- 外出先アクセスは当面対応しない
</scope>

## 2. 機能要件・技術要件

### 2.1 機能要件（MVPスコープ確定版）

#### 2.1.1 在庫管理機能
| # | 項目 | 優先度 | MVP実装内容 |
|---|-----|------|------------|
| F-INV-01 | 在庫登録 | 必須 | 手動入力のみ（バーコード・画像認識はPhase 2） |
| F-INV-02 | カテゴリ分類 | 必須 | 冷蔵/冷凍/パントリー/常温/調味料 |
| F-INV-03 | 数量・単位管理 | 必須 | g, 個, 本, パック等。開封済みフラグ |
| F-INV-04 | 賞味期限管理 | 必須 | 期限日表示、画面上の警告色 |
| F-INV-05 | 消費記録 | 必須 | 献立調理時の自動減算 / 手動修正 |
| F-INV-06 | 食材マスタ | 推奨 | 共通DB（栄養素、標準保存期間） |
| F-INV-07 | 在庫検索 | 必須 | カテゴリ・名称・期限による絞り込み |
| F-INV-08 | 購入履歴 | 推奨 | 頻度・消費パターン分析 |

#### 2.1.2 献立・レシピ提案機能
| # | 項目 | 優先度 | MVP実装内容 |
|---|-----|------|------------|
| F-MEAL-01 | 1週間献立提案 | 必須 | 朝/昼/夕の粒度 |
| F-MEAL-02 | 在庫優先利用 | 必須 | 在庫食材を最大活用 |
| F-MEAL-03 | 期限切迫優先 | 必須 | 期限近い食材から消費 |
| F-MEAL-04 | 家族構成考慮 | 必須 | MVPは大人2名向け、離乳食はPhase 2 |
| F-MEAL-05 | 栄養バランス | 推奨 | 1日/1週間単位 |
| F-MEAL-06 | アレルギー対応 | 推奨 | プロファイルにアレルゲン登録、除外 |
| F-MEAL-07 | 嗜好フィードバック | 推奨 | 献立評価記録 |
| F-MEAL-08 | 買い物リスト生成 | 必須 | 不足食材の自動リスト化 |
| F-MEAL-09 | レシピ詳細 | 必須 | LLM(Sonnet)生成、調理手順、所要時間 |
| F-MEAL-10 | 献立差し替え | 必須 | 提案後のユーザー手動修正 |

#### 2.1.3 レシピDB機能（v0.3新規セクション）
| # | 項目 | 優先度 | MVP実装内容 |
|---|-----|------|------------|
| F-RECIPE-01 | レシピDB蓄積 | 必須 | LLM生成レシピを全てDB保存（材料・手順・調理時間・コスト含む） |
| F-RECIPE-02 | レシピ再利用 | 必須 | 過去生成済みレシピを優先利用してLLMコスト削減 |
| F-RECIPE-03 | レシピ検索 | 必須 | 食材・カテゴリ・調理時間で絞り込み |
| F-RECIPE-04 | レシピ評価 | 推奨 | 家族の評価記録（星評価＋コメント） |
| F-RECIPE-05 | お気に入り | 推奨 | お気に入り登録、定番化 |

#### 2.1.4 通知機能
- **MVP**: 通知なし（画面確認のみ）
- 期限切迫品は在庫一覧画面で色分け強調表示
- Phase 2以降にLINE Bot等を検討

### 2.2 技術要件

#### 2.2.1 フロントエンド
- **GUI形態**: PWA（候補スタック: React + Vite、詳細設計時に確定）
- **入力方法**: テキスト・数値入力中心、カメラ/バーコードはPhase 2
- **オフライン動作**: 在庫照会のみ Service Worker でオフライン可

#### 2.2.2 バックエンド・エージェント層
- **エージェントFW**: LangGraph
- **API層**: FastAPI
- **エージェント構成**（v0.3更新）:
  - 在庫管理エージェント（CRUD）
  - 献立提案エージェント（プランニング）
  - **レシピ生成エージェント**（LLM生成 + DB照会・蓄積）
  - 買い物リスト生成エージェント

#### 2.2.3 データ層（D-02確定）
- **SQLiteファイル本体**: 自宅PC ローカルSSD
- **NAS の役割**:
  - SQLiteの日次バックアップ保管
  - 画像ファイル（レシピ画像等）の保存
- **バックアップ方針**:
  - 日次でSQLiteのスナップショットをNASへ転送（cron + sqlite3 .backup）
  - NAS側でRAID + 定期スナップショット
  - 復旧手順をRunbookとしてドキュメント化

#### 2.2.4 LLM選定（D-07確定: 用途で使い分け）
| 用途 | モデル | 理由 |
|-----|--------|------|
| インテントルーティング | Haiku | 軽量・低コスト・低レイテンシ |
| 在庫操作の自然言語パース | Haiku | 構造化抽出中心 |
| 献立提案（プランニング） | Sonnet | 創造性・複雑な制約考慮 |
| **レシピ生成・詳細化** | **Sonnet** | **自然な文章品質、料理ドメインの知識量** |
| 結果検証・バリデーション | Haiku | 簡易チェック |

予算想定: 月¥1,500〜3,000程度。レシピDB蓄積により呼び出し頻度を段階的に削減。

#### 2.2.5 レシピ供給源（D-08改訂版）
- **MVP戦略**: **LLM(Sonnet)生成のみ**
  - 在庫食材＋家族プロファイル＋制約を1プロンプトで処理
  - 生成されたレシピを必ずDBに蓄積（F-RECIPE-01）
  - 既存DB内に該当レシピがあれば優先再利用（F-RECIPE-02）してLLMコスト削減
- **MVPで外部レシピAPIを使わない理由**:
  - 楽天レシピAPIは食材検索ができない（カテゴリランキングTOP4のみ）
  - 規約上「特定の人のみアクセスできる環境での利用」が原則禁止（家庭内LAN利用はグレーゾーン）
  - 詳細は「楽天レシピAPI調査レポート」参照
- **Phase 2 で検討**:
  - 楽天レシピAPI（週次バッチでカテゴリランキングを取得→DB蓄積→RAGコンテキスト注入）
  - 必要に応じてSpoonacular等の代替も検討

#### 2.2.6 インフラ・運用（D-01, D-04確定）
- **サーバー**: 自宅PC（常時稼働）＋ Docker Compose
- **コンテナ構成**:
  - frontend（nginx + PWA静的配信）
  - backend（FastAPI）
  - agent-worker（LangGraph）
  - reverse-proxy（Caddy + mkcert）
- **ネットワーク**: LAN内限定、外部公開なし
- **HTTPS**: PWA要件のため mkcert で家庭用証明書発行、家族端末にroot CA配布
- **DNS**: ルータ or AdGuard Home で `kitchen.local` 等の名前解決

### 2.3 非機能要件
| カテゴリ | 要件 |
|---------|-----|
| 性能 | 在庫照会 < 1秒、献立提案応答 < 30秒、レシピ提案 < 15秒 |
| 可用性 | 平日朝・夕の利用時間帯に稼働、稼働率95%目標 |
| セキュリティ | LAN内限定、APIキー秘匿、家族外アクセス不可 |
| 保守性 | コンテナベース、設定外出し、IaC |
| プライバシー | LLM/外部APIへ送信するデータは最小限 |
| 拡張性 | エージェント追加容易、Phase 2機能の組込余地 |

## 3. ロードマップ（v0.3更新版）

### Phase 0: PoC（2〜4週間）
- 在庫CRUD（手動入力）最小UI
- LLMによる単発献立生成
- ローカルSQLite で動作確認
- LangGraph での簡易エージェント構成

### Phase 1: MVP（1〜2ヶ月）← 本要件定義スコープ
- PWA として家族で日常利用可能
- 在庫を考慮した1週間献立提案（大人2名向け）
- **食材指定レシピ提案（F-MEAL-11）**
- **レシピDB蓄積・再利用（F-RECIPE-01〜03）**
- 買い物リスト自動生成
- SQLite(PCローカル) + NAS日次バックアップ
- Docker Compose 構成での自宅PC運用
- 画面上での期限切迫色分け表示

### Phase 2: 機能拡充
- 離乳食フェーズ対応（誕生日からの自動算出）
- 画像認識・バーコードによる在庫登録
- 栄養バランス分析
- **楽天レシピAPI連携検討（週次バッチでDB蓄積→RAG活用）**
- 献立評価フィードバックループ（嗜好学習）
- LINE Bot による通知

### Phase 3: 高度化
- ローカルLLM化検討（edge AI 知見活用）
- 外出先アクセス（Tailscale等のVPN）
- マルチユーザー識別・個別嗜好管理
- 蓄積したレシピDBの本格活用（高度なRAG）

## 5. 用語
| 用語 | 定義 |
|-----|-----|
| エージェント | LangGraphで実装する、特定タスクを持つ自律的処理単位 |
| 在庫トランザクション | 入出庫・消費・廃棄の履歴レコード |
| 食材マスタ | 食材の共通属性（栄養素・保存期間等）を持つマスタDB |
| 家族プロファイル | 家族メンバーの属性（嗜好・アレルギー等） |
| MVP | Minimum Viable Product。日常運用に乗せられる最小機能セット |
| **食材指定レシピ提案** | **使用優先度の高い食材を起点として、その食材を使うレシピを即時1〜3案提案する機能** |
