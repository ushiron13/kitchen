## 0. 背景と目的

現行システムは自宅 PC を常時稼働させる前提（D-01）で構築されているが、以下の課題がある。

| 課題 | 内容 |
|------|------|
| サーバー稼働コスト | 自宅 PC を 24h 常時稼働させる電力・管理コスト |
| 可用性の制約 | PC が落ちると家族全員が利用不可 |
| アクセス範囲 | 家庭内 LAN 限定（D-04）のため外出先で使えない |
| インストール体験 | Safari の「ホーム画面に追加」で即インストールできるが、サーバーが存在しないと URL を開けない |

**目的**: バックエンドサーバーを完全に廃止し、**GitHub Pages にホストされた純粋クライアントサイド PWA** として動作させることで、サーバー不要・iPad ホーム画面アプリ化を実現する。

## 1. アーキテクチャ変更の決定事項

| ID | 論点 | 旧決定 (v0.3) | 新決定 |
|----|------|--------------|-------|
| D-01改 | サーバー稼働形態 | 自宅PC常時稼働 | **サーバーなし（GitHub Pages 静的ホスティング）** |
| D-02改 | DB配置 | SQLite (PCローカル) + NASバックアップ | **IndexedDB（iPad/ブラウザ内）** |
| D-04改 | 外出先利用 | LAN内限定 | **インターネット接続があればどこでも利用可能** |
| D-10新 | API キー管理 | バックエンド環境変数 | **ユーザーが初回設定画面から入力 → localStorage 保存** |
| D-11新 | バックエンド言語 | Python (FastAPI + LangGraph) | **廃止。AI 呼び出しは Anthropic JS SDK でブラウザから直接** |
| D-12新 | データ同期 | N/A（単一DB） | **MVP はデバイス内完結（マルチデバイス同期は Phase 2）** |

## 2. 機能要件

### 2.1 引き継ぐ機能（変更なし）

既存の全機能（F-INV-01〜08、F-MEAL-01〜11、F-RECIPE-01〜05）をそのまま維持する。
UI の操作感・見た目も原則変更しない。

### 2.2 変更が生じる機能

| 機能 | 変更内容 |
|------|---------|
| F-INV-01〜08 在庫管理 | データ永続化先を SQLite → **IndexedDB** に切り替え。操作 UI は維持 |
| F-MEAL-01 献立提案 | LangGraph エージェントを廃止。**Anthropic JS SDK** を使ったブラウザ内関数に置き換え |
| F-MEAL-09 レシピ詳細 | 同上。Sonnet を直接呼び出してレシピ生成 |
| F-MEAL-11 食材指定レシピ | 同上 |
| F-RECIPE-01〜03 レシピ DB | IndexedDB 上のレシピテーブルで DB 蓄積・再利用を維持 |
| API キー入力 | 既存の `kitchen_api_key` localStorage 設計を活用。初回起動時にキー入力画面を表示 |

### 2.3 新規追加機能

| ID | 機能 | 内容 |
|----|------|------|
| F-EXPORT-01 | データエクスポート | 在庫・レシピ・献立データを JSON でダウンロード（バックアップ用） |
| F-IMPORT-01 | データインポート | JSON ファイルから IndexedDB へリストア（デバイス移行・バックアップ復元用） |

### 2.4 廃止機能

| 廃止対象 | 理由 |
|---------|------|
| FastAPI バックエンド全般 | クライアントサイドに統合 |
| LangGraph エージェント | Anthropic JS SDK の直接呼び出しに置き換え |
| Docker Compose 構成 | サーバーが不要になるため |
| Caddy (HTTPS 終端) | GitHub Pages が HTTPS を提供するため |
| NAS バックアップ連携 | F-EXPORT-01 の手動エクスポートに置き換え |

## 3. 技術要件

### 3.1 フロントエンド

| 項目 | 現行 | 移行後 |
|------|------|-------|
| フレームワーク | React 18 + Vite | React 18 + Vite（維持） |
| 言語 | TypeScript | TypeScript（維持） |
| PWA | vite-plugin-pwa + Workbox | 維持。キャッシュ戦略を API → IndexedDB 向けに変更 |
| データ層 | fetch → FastAPI → SQLite | **Dexie.js（IndexedDB ラッパー）** |
| AI 呼び出し | fetch → FastAPI → LangGraph → Anthropic | **@anthropic-ai/sdk（ブラウザ直接呼び出し）** |
| スタイリング | インラインスタイル | 維持（変更なし） |

### 3.2 データ層詳細

```
Dexie.js (IndexedDB)
  ├── foods          — 食材マスタ
  ├── stockItems     — 在庫アイテム
  ├── stockTransactions — 在庫トランザクション履歴
  ├── mealPlans      — 献立プラン
  ├── meals          — 個別献立
  ├── recipes        — レシピ（LLM 生成分の蓄積）
  ├── recipeIngredients — レシピ食材
  └── profile        — 家族プロファイル（1 件）
```

- **マイグレーション管理**: Dexie のバージョニング機能（`db.version(N).stores()`）でスキーマ変更を管理
- **ID 管理**: 自動採番（`++id`）でサーバーの採番に依存しない設計

### 3.3 AI 呼び出し層

- **ライブラリ**: `@anthropic-ai/sdk`（ブラウザ対応版）
- **使用モデル**: 現行と同じく Haiku（軽量処理）/ Sonnet（献立・レシピ生成）を使い分け
- **API キー**: ユーザーが設定画面から入力、`localStorage` に保存
- **プロンプト**: 既存バックエンドのプロンプトをフロントエンドの関数として移植
- **オフライン時**: ネットワークエラーをキャッチして「インターネット接続が必要です」と表示

### 3.4 ホスティング

- **サービス**: GitHub Pages
- **デプロイ**: `main` ブランチへのマージ時に GitHub Actions で `vite build` → `gh-pages` ブランチにデプロイ
- **URL**: `https://<username>.github.io/<repo-name>/`
- **HTTPS**: GitHub Pages が自動提供（PWA 要件を満たす）
- **セキュリティ**: データは閲覧者自身の IndexedDB に閉じているため、URL が公開されても他者のデータにはアクセスできない

### 3.5 iPad へのインストール手順

1. Safari で `https://<username>.github.io/<repo-name>/` を開く
2. 画面下部の共有ボタン（□↑）をタップ
3. 「ホーム画面に追加」→「追加」
4. ホーム画面のアイコンから起動（`display: standalone` により全画面で表示）

## 4. 非機能要件

| カテゴリ | 要件 |
|---------|------|
| 性能 | 在庫照会 < 100ms（IndexedDB はローカルアクセスのため高速）、献立提案 < 30s（Claude API 依存） |
| オフライン動作 | 在庫照会・レシピ閲覧・献立参照は完全オフライン動作。AI 生成機能はオンライン必須 |
| データ保全 | F-EXPORT-01 によるユーザー主導のバックアップ。デバイス初期化・ブラウザデータ消去で消失するリスクをユーザーに周知 |
| セキュリティ | API キーは localStorage のみに保存（他者の端末からはアクセス不可）。GitHub Pages は静的ファイルのみ配信（サーバーサイドロジックなし） |
| マルチデバイス | MVP はデバイス内完結。夫婦 2 台で共有する場合は JSON エクスポート/インポートで手動同期 |

## 5. 実装フェーズ

### Phase 1: データ層移行（優先度: 高）
1. Dexie.js インストール・スキーマ定義
2. `makeApi()` の全メソッドを Dexie CRUD に置き換え（API 呼び出しを廃止）
3. 既存 UI のデータバインディングが Dexie 経由で動作することを確認

### Phase 2: AI 層移行（優先度: 高）
1. `@anthropic-ai/sdk` インストール
2. 献立生成ロジック（LangGraph `build_skeleton_graph` 相当）を TypeScript 関数として移植
3. レシピ生成ロジック同上
4. API キー設定画面の追加（初回起動フロー）

### Phase 3: データ移行補助（優先度: 中）
1. F-EXPORT-01: JSON エクスポート機能実装
2. F-IMPORT-01: JSON インポート機能実装

### Phase 4: デプロイ設定（優先度: 高）
1. `vite.config.ts` のベースパス設定（GitHub Pages 向け）
2. GitHub Actions ワークフロー作成（push → build → deploy）
3. サービスワーカーのキャッシュ戦略更新（API キャッシュ → 静的アセットキャッシュに変更）

### Phase 5: 動作確認・リリース
1. iPad Safari 実機確認
2. ホーム画面追加・スタンドアロン表示確認
3. オフライン動作確認（機内モードテスト）

## 6. リスクと対策

| リスク | 影響 | 対策 |
|--------|------|------|
| IndexedDB データ消失 | Safari の「履歴とWebサイトデータを消去」等でデータが全消去される | F-EXPORT-01 での定期バックアップを UI 上で促す |
| API キー露出 | 端末盗難時に localStorage のキーが読み取られる可能性 | Anthropic のダッシュボードでキーを無効化できることを案内。MVPではこの範囲で許容 |
| Claude API コスト | バックエンドがなくなりリクエスト制御がなくなる | フロントエンドで連打防止（ローディング中は送信不可）を実装 |
| Safari の IndexedDB 容量 | Safari は IndexedDB に 1GB 程度の制限（実用上は問題になりにくい） | 許容範囲として MVP では対策しない |
| マルチデバイス同期 | 夫婦 2 台で IndexedDB が独立する | MVP は手動 JSON 同期。Phase 2 で CloudFlare KV 等を検討 |
