## 1. バグ（Phase 1 hotfix 対象）

### B-01: レシピ参照のたびに reuse_count が増加する ✅ 完了

**現象**
既にレシピが紐づいている献立で「レシピ詳細」ボタンを押すたびに `reuse_count` が +1 される。

**根本原因**
フロントエンドがレシピ「参照」に `POST /api/v1/meals/{id}/recipe` を呼んでいる。このエンドポイントは「生成または再利用」の操作であり、既存レシピが見つかるたびに `increment_reuse` を実行する設計になっている。参照と生成が同一エンドポイントに混在している。

**修正内容**（commit 441dafc）
- Backend: `meal.recipe_id == existing.id` の場合は `increment_reuse` をスキップ
- Frontend: レシピ表示ボタンを `meal.recipe_id` の有無で分岐し、既存レシピは `GET /recipes/{id}` で参照

---

### B-02: 画面遷移後にレシピモーダルが自動表示される ✅ 完了

**現象**
レシピ生成後に別タブ（在庫・買い物）へ遷移し、献立タブに戻ると直前に生成したレシピのモーダルが自動で開く。

**根本原因**
`useEffect(() => { loadRecipe() }, [meal.recipe_id])` が MealCard マウント時にレシピを自動ロードし、ロード完了でモーダルが開く設計だった。

**修正内容**（commit 441dafc）
- `useEffect` 自動ロードを削除
- `loadedRecipe`（データ）と `showModal`（UI表示フラグ）を分離
- モーダルはユーザーのボタン操作時のみ開く

---

### B-03: 要望テキスト入力時に献立生成が失敗する ✅ 完了

**現象**
`preferences`（要望）フィールドに日本語テキストを入力して献立生成すると、以下のエラーが発生する（2026-06-06 11:52–11:54 ログ確認済み）：
```
Skeleton parse error: Expecting value: line 118 column 29
Skeleton parse error: Unterminated string starting at: line 118 column 63
```

**根本原因**
`max_tokens=2048` で多食事区分・日数の場合に JSON 出力が途中で切れる。

**修正内容**（commit 97f4ae7）
- `max_tokens` を 2048 → 4096 に拡張
- `_extract_json_array()` 関数を追加し、余分なテキストや不完全な JSON からでも `[...]` ブロックを regex で抽出するフォールバックを実装

### F-08: 好み学習に基づく献立提案の改善（Phase 3 候補）

**背景**
F-07 で蓄積される `meal.status`（cooked/skipped）と `meal_feedback`（satisfaction, skip_reason）を使い、ユーザーの嗜好を献立生成プロンプトに自動反映する。

**蓄積データの活用方針**

| シグナル | ソース | 活用方法 |
|---------|-------|---------|
| cooked 率が高いコンセプト | `meal.status = 'cooked'` | プロンプトに「好みの傾向」として注入 |
| skipped が多い meal_type・食材 | `meal.status = 'skipped'` | 「避けたい傾向」として注入 |
| skip_reason テキスト | `meal_feedback.skip_reason` | 将来: NLP でカテゴリ分類し構造化 |
| satisfaction スコア平均 | `meal_feedback.satisfaction` | 評価の高いレシピを再利用優先 |

**集計クエリ例（好み抽出）**
```sql
-- cooked 率が高い meal_type を抽出
SELECT meal_type,
       COUNT(*) AS total,
       SUM(CASE WHEN status = 'cooked' THEN 1 ELSE 0 END) AS cooked_count,
       ROUND(100.0 * SUM(CASE WHEN status = 'cooked' THEN 1 ELSE 0 END) / COUNT(*), 1) AS cooked_rate
FROM meal
GROUP BY meal_type
ORDER BY cooked_rate DESC;

-- 最近 30 日で skipped が多かったコンセプト
SELECT concept, COUNT(*) AS skip_count
FROM meal
WHERE status = 'skipped'
  AND created_at >= datetime('now', '-30 days')
GROUP BY concept
ORDER BY skip_count DESC
LIMIT 10;
```

**設計方針（Phase 3 着手時に具体化）**
- DB: `meal_feedback` に蓄積（migration 002 で追加済み）
- API: `GET /api/v1/preference-summary` → 統計を返す
- Agent: スケルトン生成プロンプトに「好み傾向」セクションを追加
  - `_build_skeleton_prompt` に `preference_summary` を引数追加
  - 直近 30 日の cooked/skipped 傾向を SystemMessage に組み込む

### F-10: 在庫ごとの保管場所（カテゴリ）上書き ✅ 完了（56495ca）

**ユーザー要望（2026-06-14）**
> 同じ食材でも冷凍と冷蔵で登録できるようにして欲しい（例: 豚肉(冷蔵)と豚肉(冷凍)）

**本質**

- `StockRead.food_category` を `stock_item.category ?? food_master.category` で算出（API 層）

- 在庫編集モーダル: `item.food_category`（effective category）を初期値として表示・変更可能
- カテゴリフィルタ: `COALESCE(stock_item.category, food_master.category)` で絞り込み（SQLAlchemy）

### F-11: レシピ Markdown レンダリング

**ユーザー要望（2026-06-14）**
> レシピの表示でマークダウンの構文が正しく表示されていないときがある

**本質**
LLM（Sonnet）はレシピ本文を Markdown 形式（`**材料**`、`## 手順`、`- 豚バラ肉 200g`）で返すが、フロントエンドはテキストをそのまま `<pre>` / plaintext で表示している。`**太字**` や `# 見出し` などの記法が生文字として見えてしまう。

**要件**
- LLM が出力する Markdown を HTML として正しくレンダリングする
- レシピモーダル内の `recipe.steps`（本文テキスト）に適用する
- XSS リスクがないように sanitize する

**実装案**
- `react-markdown`（+ `remark-gfm`）を導入し、レシピ本文を `<ReactMarkdown>` でラップ
- または軽量な `marked` + DOMPurify で HTML 文字列に変換してから `dangerouslySetInnerHTML`
- 追加 JS バンドルサイズが気になる場合は `micromark` など最小構成を選択

**F-12 との関係**
F-12 でプロンプトを統一すると Markdown の構造が安定し、F-11 のスタイリングが簡単になる。セットで実装することを推奨。

### F-12: レシピ生成フォーマット統一（プロンプト）

- システムプロンプトに「必ずこのフォーマットで出力せよ」という制約を明記
- 必要なら Pydantic スキーマで構造化出力（structured output）を強制する方法も検討

### F-13: オフライン献立閲覧（PWA API キャッシュ）

**ユーザー要望（2026-06-14）**
> サーバーを起動してないときでも、生成や編集はできなくて良いので、献立を見れるようにしたい

**本質**
現在の PWA Service Worker は静的アセット（JS/CSS）をキャッシュするが、API レスポンスはキャッシュしない。バックエンドが落ちている状態では画面が真っ白になる。ユーザーは「読むだけ」であればオフラインで機能してほしいと考えている。

**要件**
- バックエンド停止中でも `/api/v1/meal-plans` の最終取得データを閲覧できる
- 在庫一覧も同様にキャッシュして参照可能にする
- 書き込み操作（生成・編集・削除）はオフライン時にエラーメッセージを表示するだけでよい

**実装案**
- `vite-plugin-pwa` の `workbox.runtimeCaching` に Network-first（失敗時は Cache fallback）戦略を追加
  ```ts
  // vite.config.ts
  runtimeCaching: [{
    urlPattern: /\/api\/v1\/(meal-plans|stock|foods)/,
    handler: 'NetworkFirst',
    options: { cacheName: 'api-cache', expiration: { maxAgeSeconds: 60 * 60 * 24 * 7 } }
  }]
  ```
- フロントエンドで `navigator.onLine` を監視し、オフライン時はバナーを表示して書き込みボタンを無効化
- API キャッシュには認証ヘッダー（`X-API-Key`）が含まれるため、HTTPS 必須（Caddy で既に対応済み）

**注意事項**
- `X-API-Key` ヘッダー付きリクエストは `vary: *` になる可能性があるため、Workbox の `cacheableResponse` プラグインで 200 レスポンスのみキャッシュするよう設定する
- Service Worker を更新するたびにキャッシュが引き継がれるか確認が必要
