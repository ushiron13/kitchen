## 1. バグ（Phase 1 hotfix 対象）

### B-01: レシピ参照のたびに reuse_count が増加する ✅ 完了

**現象**
既にレシピが紐づいている献立で「レシピ詳細」ボタンを押すたびに `reuse_count` が +1 される。

**根本原因**
フロントエンドがレシピ「参照」に `POST /api/v1/meals/{id}/recipe` を呼んでいる。このエンドポイントは「生成または再利用」の操作であり、既存レシピが見つかるたびに `increment_reuse` を実行する設計になっている。参照と生成が同一エンドポイントに混在している。

**修正内容**（commit 441dafc）
- Backend: `meal.recipe_id == existing.id` の場合は `increment_reuse` をスキップ
- Frontend: レシピ表示ボタンを `meal.recipe_id` の有無で分岐し、既存レシピは `GET /recipes/{id}` で参照

---

### B-02: 画面遷移後にレシピモーダルが自動表示される ✅ 完了

**現象**
レシピ生成後に別タブ（在庫・買い物）へ遷移し、献立タブに戻ると直前に生成したレシピのモーダルが自動で開く。

**根本原因**
`useEffect(() => { loadRecipe() }, [meal.recipe_id])` が MealCard マウント時にレシピを自動ロードし、ロード完了でモーダルが開く設計だった。

**修正内容**（commit 441dafc）
- `useEffect` 自動ロードを削除
- `loadedRecipe`（データ）と `showModal`（UI表示フラグ）を分離
- モーダルはユーザーのボタン操作時のみ開く

---

### B-03: 要望テキスト入力時に献立生成が失敗する ✅ 完了

**現象**
`preferences`（要望）フィールドに日本語テキストを入力して献立生成すると、以下のエラーが発生する（2026-06-06 11:52–11:54 ログ確認済み）：
```
Skeleton parse error: Expecting value: line 118 column 29
Skeleton parse error: Unterminated string starting at: line 118 column 63
```

**根本原因**
`max_tokens=2048` で多食事区分・日数の場合に JSON 出力が途中で切れる。

**修正内容**（commit 97f4ae7）
- `max_tokens` を 2048 → 4096 に拡張
- `_extract_json_array()` 関数を追加し、余分なテキストや不完全な JSON からでも `[...]` ブロックを regex で抽出するフォールバックを実装

### F-05: ユーザープロファイル（固定嗜好・家族構成）

**抽象化**
献立生成の `preferences` には「そのとき限りの要望（今日は魚が食べたい）」と「常に適用したいプロファイル（大人2名・朝はパン・昼は麺類）」が混在している。後者を毎回入力するのはUXとして非効率。

**要件**
- 設定画面でプロファイルを登録・編集できる
  - 家族構成（大人2名 etc.）
  - 食事傾向（朝: 簡単に / 昼: 麺類 / 夜: 和食多め）
  - アレルギー・禁忌食材
- 献立生成時にプロファイルをシステムプロンプトへ自動注入
- `preferences` フィールドはその日の一時的な追加要望のみに限定

**設計方針案**
- DB: `user_profile` テーブル（KV 形式 or 単一 JSON カラム）
- API: `GET/PUT /api/v1/profile`
- Agent: `_build_skeleton_prompt` でプロファイルを `SystemMessage` に組み込む

### F-03: 食材の保存日数目安表示

**抽象化**
野菜・肉・魚など生鮮食材は保存期限が短く、視覚的に「あと何日」を示すことで廃棄削減につながる。

**要件**
- 在庫登録時に「購入日」または「消費期限」を任意入力できる
- 食材カテゴリ別にデフォルト保存日数（野菜: 5日、肉: 2日など）を設定し、購入日から算出した目安を表示
- 期限切迫（3日以内）には警告色を表示

**スキーマ拡張候補**
```sql
ALTER TABLE stock ADD COLUMN purchased_date TEXT;
ALTER TABLE stock ADD COLUMN expiry_date TEXT;
ALTER TABLE food ADD COLUMN default_shelf_life_days INTEGER;
```

### F-08: 好み学習に基づく献立提案の改善（Phase 3 候補）

**背景**
F-07 で蓄積される `meal.status`（cooked/skipped）と `meal_feedback`（satisfaction, skip_reason）を使い、ユーザーの嗜好を献立生成プロンプトに自動反映する。

**蓄積データの活用方針**

| シグナル | ソース | 活用方法 |
|---------|-------|---------|
| cooked 率が高いコンセプト | `meal.status = 'cooked'` | プロンプトに「好みの傾向」として注入 |
| skipped が多い meal_type・食材 | `meal.status = 'skipped'` | 「避けたい傾向」として注入 |
| skip_reason テキスト | `meal_feedback.skip_reason` | 将来: NLP でカテゴリ分類し構造化 |
| satisfaction スコア平均 | `meal_feedback.satisfaction` | 評価の高いレシピを再利用優先 |

**集計クエリ例（好み抽出）**
```sql
-- cooked 率が高い meal_type を抽出
SELECT meal_type,
       COUNT(*) AS total,
       SUM(CASE WHEN status = 'cooked' THEN 1 ELSE 0 END) AS cooked_count,
       ROUND(100.0 * SUM(CASE WHEN status = 'cooked' THEN 1 ELSE 0 END) / COUNT(*), 1) AS cooked_rate
FROM meal
GROUP BY meal_type
ORDER BY cooked_rate DESC;

-- 最近 30 日で skipped が多かったコンセプト
SELECT concept, COUNT(*) AS skip_count
FROM meal
WHERE status = 'skipped'
  AND created_at >= datetime('now', '-30 days')
GROUP BY concept
ORDER BY skip_count DESC
LIMIT 10;
```

**設計方針（Phase 3 着手時に具体化）**
- DB: `meal_feedback` に蓄積（migration 002 で追加済み）
- API: `GET /api/v1/preference-summary` → 統計を返す
- Agent: スケルトン生成プロンプトに「好み傾向」セクションを追加
  - `_build_skeleton_prompt` に `preference_summary` を引数追加
  - 直近 30 日の cooked/skipped 傾向を SystemMessage に組み込む
