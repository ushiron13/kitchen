## 1. バグ（Phase 1 hotfix 対象）

### B-01: レシピ参照のたびに reuse_count が増加する

**現象**
既にレシピが紐づいている献立で「レシピ詳細」ボタンを押すたびに `reuse_count` が +1 される。

**根本原因**
フロントエンドがレシピ「参照」に `POST /api/v1/meals/{id}/recipe` を呼んでいる。このエンドポイントは「生成または再利用」の操作であり、既存レシピが見つかるたびに `increment_reuse` を実行する設計になっている。参照と生成が同一エンドポイントに混在している。

**あるべき設計**
- レシピが未生成 → 「生成」ボタン → `POST /meals/{id}/recipe`（生成 or 再利用）
- レシピ生成済み → 「詳細を見る」ボタン → `GET /recipes/{recipe_id}`（参照のみ、カウント変化なし）
- `reuse_count` は「別の meal に同一レシピをアタッチした回数」として定義を明確化

---

### B-02: 画面遷移後にレシピモーダルが自動表示される

**現象**
レシピ生成後に別タブ（在庫・買い物）へ遷移し、献立タブに戻ると直前に生成したレシピのモーダルが自動で開く。

**根本原因**
フロントエンドの `openRecipe: Recipe | null` 状態がページコンポーネントの外側（App レベル）に保持されており、タブ遷移でリセットされない。

**修正方針**
- タブ切り替え時に `openRecipe` を `null` にリセットする
- または `openRecipe` の管理を `MealPlanPage` 内ローカル状態に移動し、ページ離脱時に自動クリアする

---

### B-03: 要望テキスト入力時に献立生成が失敗する

**現象**
`preferences`（要望）フィールドに日本語テキストを入力して献立生成すると、以下のエラーが発生する（2026-06-06 11:52–11:54 ログ確認済み）：
```
Skeleton parse error: Expecting value: line 118 column 29
Skeleton parse error: Unterminated string starting at: line 118 column 63
```

**根本原因**
`_build_skeleton_prompt` がユーザー入力テキストをプロンプトに直接埋め込んでいる。入力に引用符・改行・バックスラッシュが含まれると LLM の JSON 出力が崩れる。`max_tokens=2048` で長い要望があると出力が途中で切れることも原因になる。

**修正方針**
1. `preferences` を JSON プロパティとして渡す（直接文字列埋め込みを避ける）
2. `max_tokens` を 3000〜4096 に増やす
3. パース失敗時に `json-repair` ライブラリまたはリトライを追加する
4. プロンプトに「要望テキストをJSONのフィールド値に含めないこと」を明示する

## 2. 機能改善（Phase 2 対象）

### F-01: 食材マスター・在庫の編集・削除 UI

**抽象化**
現在の在庫管理 UI は「追加」のみ。実運用では「名前の修正」「カテゴリ変更」「数量の上書き」「不要な食材の削除」が頻繁に発生する。CRUD の C のみ実装されている状態。

**要件**
- 食材マスター: 名前・カテゴリの編集、削除（参照がある場合は論理削除）
- 在庫: 数量・単位の編集（上書き更新）、行削除
- UI: インライン編集またはモーダル編集（タップで編集モードに入る）

---

### F-02: 食材カテゴリによる絞り込み・並び替え

**抽象化**
食材マスターと在庫一覧が増えるにつれ、目的の食材を探すコストが上がる。`food.category` フィールド（`refrigerated` / `frozen` / `pantry` 等）は DB に既存だが、フロントエンドで活用されていない。

**要件**
- 在庫一覧でカテゴリタブ（冷蔵 / 冷凍 / 常温）または絞り込みチップ
- カテゴリ内でのアルファベット・五十音順ソート
- 将来的には食材マスターの「ジャンル」（野菜・肉・魚・調味料等）の細分化も検討

**注**: 現 `category` は保存場所ベース（冷蔵・冷凍・常温）。「食材の種類」はサブカテゴリとして追加が望ましい。スキーマ拡張を検討。

---

### F-03: 食材の保存日数目安表示

**抽象化**
野菜・肉・魚など生鮮食材は保存期限が短く、視覚的に「あと何日」を示すことで廃棄削減につながる。

**要件**
- 在庫登録時に「購入日」または「消費期限」を任意入力できる
- 食材カテゴリ別にデフォルト保存日数（野菜: 5日、肉: 2日など）を設定し、購入日から算出した目安を表示
- 期限切迫（3日以内）には警告色を表示

**スキーマ拡張候補**
```sql
ALTER TABLE stock ADD COLUMN purchased_date TEXT;
ALTER TABLE stock ADD COLUMN expiry_date TEXT;
ALTER TABLE food ADD COLUMN default_shelf_life_days INTEGER;
```

---

### F-04: レシピ「生成」と「参照」ボタンの明確な分離

**抽象化**
B-01 の修正と連動。現在の UX は「レシピ生成 → ボタンが切り替わってレシピ詳細になる」という状態変化が直感的でない。生成済みと未生成で異なる操作体系をはっきり分けることで混乱を防ぐ。

**要件**
- スケルトン状態（`recipe_id == null`）: 「レシピを生成する」ボタンのみ表示
- レシピあり状態（`recipe_id != null`）: 「レシピを見る」ボタンのみ表示。生成ボタンは非表示
- 折り畳み表示での詳細展開も可

---

### F-05: ユーザープロファイル（固定嗜好・家族構成）

**抽象化**
献立生成の `preferences` には「そのとき限りの要望（今日は魚が食べたい）」と「常に適用したいプロファイル（大人2名・朝はパン・昼は麺類）」が混在している。後者を毎回入力するのはUXとして非効率。

**要件**
- 設定画面でプロファイルを登録・編集できる
  - 家族構成（大人2名 etc.）
  - 食事傾向（朝: 簡単に / 昼: 麺類 / 夜: 和食多め）
  - アレルギー・禁忌食材
- 献立生成時にプロファイルをシステムプロンプトへ自動注入
- `preferences` フィールドはその日の一時的な追加要望のみに限定

**設計方針案**
- DB: `user_profile` テーブル（KV 形式 or 単一 JSON カラム）
- API: `GET/PUT /api/v1/profile`
- Agent: `_build_skeleton_prompt` でプロファイルを `SystemMessage` に組み込む
